# ADR 0003 — P1.4 curriculum/batch backend first; admin UI + Playwright grouped with P1.8

- **Status:** Accepted
- **Date:** 2026-07-15
- **Context:** P1.4 Curriculum + batches

## Context

P1.4 (PRD §6.1, §6.2) calls for the curriculum hierarchy and batch/roster
management **in the admin portal**, plus a Playwright test of the admin
create-batch-and-roster flow.

The admin UI is authenticated, role-gated (admin/trainer). But per **ADR 0002**
the API-auth mechanism and the actual portal shell/login are deferred to **P1.8**
(Sanctum not installed; SPA-vs-token decision is frontend-coupled). Building
admin CRUD screens now would require throwaway auth stubs, and any Playwright
flow would exercise that stub rather than the real gated portal.

## Decision

Deliver the complete, fully-tested **P1.4 backend** now and group the admin UI +
Playwright with **P1.8**, when the portal shell and auth exist to host them.

**Delivered now (tested, on SQLite — 37 P1.4 assertions across 19 tests):**

- Curriculum: `programs → courses → modules → topics → lessons` models +
  migrations (tenant-scoped, FK+indexes), `LessonType` enum.
- Batches: `Batch` + `BatchMember` with `BatchType` / `BatchMemberStatus` enums;
  `CreateBatch` generates `{COURSE}-{YYYYMM}-{seq}` with manual override and
  per-tenant uniqueness; capacity guard on the model.
- Roster: `AddStudentToBatch` (silo, capacity + same-tenant + dup guards),
  `BulkAddStudentsToBatch`, `ImportRosterCsv` (name,phone,email; per-row error
  reporting), `TransferBatchMember`, `RemoveBatchMember` — all audited;
  `FindOrCreateStudent` intake.
- Events: `TopicCompleted` / `ModuleCompleted` fired by `MarkTopicCompleted`
  (idempotent; module fires when its last topic completes). Listeners later.
- Seed: 7 BrowseJobs courses with a sample module/topic/lesson tree.

**Deferred to P1.8 (with the portal shell + auth):**

- Admin CRUD screens for curriculum + batches + roster (Next.js, React Query,
  loading/empty/error states).
- HTTP controllers + Form Requests + API Resources exposing these actions, and
  the role-gated route groups that protect them.
- The Playwright create-batch-and-roster flow (needs the gated portal to drive).

## Consequences

- Every logic-bearing part of P1.4 (numbering, capacity, roster ops, audit,
  completion events) is done and covered; the UI/HTTP layer over it is thin.
- **P1.4 is not 100% of its playbook bullet.** The deferred UI/HTTP/Playwright
  items must land in P1.8 alongside the P1.3 login endpoints — tracked here and
  in ADR 0002. P1.8 is now the consolidated "frontend + API-auth" milestone.

## Alternatives considered

- **Build admin screens with a dev-only auth stub now:** rejected — throwaway
  work and a Playwright flow that proves the stub, not the product.
