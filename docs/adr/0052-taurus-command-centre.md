# ADR 0052 — Taurus AI command centre (multi-workspace live agent console)

- **Status:** Accepted
- **Date:** 2026-10-09
- **Relates to:** ADR 0016 (multi-LLM provider config), ADR 0039 (platform settings), ADR 0051 (employer workspaces)

## Context

The founder runs a growing set of AI bots (n8n flows, scripts, scrapers, outreach agents)
across two kinds of work: company operations and recruitment. There was no single place to see
what each bot is doing, which ones have gone quiet, what they have spent, or — most importantly
— to stop a bot from doing something risky (sending mail, paying a vendor) without a human
saying yes. Employer clients want the same picture of their hiring pipeline.

Before deployment the product owner turned Taurus into a SaaS: every business, the founder
included, gets its own Taurus **workspace** with its own agents, bot token and LLM / ElevenLabs
keys. A client sees only their workspace; the founder's agents and keys are invisible to clients.

## Decision

1. **Workspaces are the unit of isolation.** `taurus_workspaces` (tenant-scoped; `slug` unique
   per tenant; `status` active|suspended; `is_owner` marks the founder's single "Taurus HQ" per
   tenant) with `taurus_workspace_members` (owner | admin | viewer), `…_credentials` and
   `…_invites`. Every Taurus data table (`taurus_agents`, `taurus_tasks`, `taurus_events`,
   `taurus_spend_events`) carries `taurus_workspace_id` (FK, cascade, indexed) and every query
   filters by it; agents are unique per (workspace, floor, slug). All tables also use
   `BelongsToTenant`, so a tenant boundary sits underneath the workspace boundary.

2. **Membership is enforced by middleware, and outsiders learn nothing.** The member API
   (`/v1/taurus/workspaces/{workspace}/…`) runs `auth:sanctum` + `tenant.user` + `taurus.member`:
   a non-member (or another tenant's workspace) gets **404**, never 403, so a workspace's
   existence is not confirmed; a suspended workspace gets 403 `workspace_suspended`;
   `taurus.member:manage` (keys, token, approvals, members) needs owner or admin, else 403
   `forbidden`. Task routes use scoped bindings, so a task id from another workspace is a 404
   even through your own workspace's URL.

3. **Bots authenticate per workspace.** The bearer token *is* the workspace: ingest looks up
   sha256(token) in `taurus_workspaces.ingest_token_hash` (unique), 401 when unknown, 403 when
   the workspace is suspended, then runs in that workspace's tenant. There is no global ingest
   token any more. Tokens are `tau_` + 40 random chars, generated by an owner/admin, shown
   exactly once (only the hash and last four are stored), audited on rotation; the old token
   stops working immediately. `decisions` returns only that workspace's decisions. Rate limit
   `taurus-ingest` = 600/min keyed by the token hash.

4. **Each workspace has its own brain and voice — clients never borrow.** Credentials live in
   `taurus_workspace_credentials` (`api_key` with the `encrypted` cast, hidden from
   serialization; only `key_last4` is shown). `App\Support\Taurus\WorkspaceBrain` is the single
   place the rule lives: a client workspace uses its own credential for `brain_provider` (or, if
   unset, the first provider it holds a key for), with model = `brain_model` ?? credential model
   ?? provider default; with no key it has **no brain (503 `brain_not_configured`) and no voice
   (204 → browser voice)**. It never falls back to the platform's keys or another workspace's.
   Only HQ may choose `platform` (a client choosing it is a 422), and HQ alone falls back to the
   platform's key for a chosen provider and to the platform ElevenLabs voice.
   `ClientFactory::fromCredentials()` builds a transport from a workspace key using only the
   provider's *shape* (driver, API version, hard-coded vendor endpoint) — never the platform key
   or a platform base-URL override — and `AiGateway::complete()` accepts that prebuilt
   `opts['client']` (alongside the existing `opts['provider']`), keeping budget and `ai_events`
   logging (`AiPurpose::Taurus`) identical. Gemini (own `gemini` driver) and Groq
   (`openai_compatible`) are added as providers.

5. **The founder's console is owner-only, by role — never by permission.**
   `/v1/admin/taurus/*` runs `taurus.owner` (`EnsureTaurusOwner`): `super-admin` role, plus —
   when `TAURUS_OWNER_EMAILS` is set — an email on that list (case-insensitive). It lists every
   workspace in the tenant with counts only (no agent data, no keys), creates client workspaces
   with an owner invite, invites members, renames/suspends (HQ cannot be suspended), and
   `POST hq` idempotently creates "Taurus HQ" with the caller as owner. It also manages the
   **platform brain** (the owner-only `taurus` platform_settings group + shared `ai` keys), which
   powers the employer hiring floor and HQ's fallback. The `taurus` group is hidden from and
   refused by the generic Admin → Settings page (`PlatformSettings::saveShared()`); keys are
   encrypted, masked, audited by key name only (ADR 0039).

6. **Clients sign up only by invite.** An invite stores sha256(token) and expires
   (`taurus.invite_ttl_days`, default 7); the raw token exists once, in
   `{FRONTEND_URL}/taurusai/claim/{token}`. `POST /v1/auth/taurus/claim` (host tenant,
   10/min) consumes it atomically: a new email becomes a `user_type = client` account; an email
   that already has an account joins only if the password matches that account, so an invite
   link can never take over an existing login. `POST /v1/auth/taurus/login` (staff-login
   throttle) signs in only users who belong to at least one active workspace, with one generic
   refusal message; accounts with two-factor sign-in are sent to the staff login. Both start the
   usual Sanctum SPA session. Client users hold no platform roles, so staff (`can:`) and employer
   (membership) surfaces refuse them.

7. **Two floors, idempotent ingest, derived offline.** `floor` is `ops` or `recruitment`; tasks
   upsert by (agent, ref). Feed lines are written only when a status actually changes. "Offline"
   is derived at read time from `last_seen_at` (`taurus.offline_after_minutes`). "Today" is the
   calendar day in `taurus.timezone` (IST).

8. **Approvals are human-only.** A bot can park a task in `needs_approval`; only a workspace
   owner/admin can approve (→ `running`) or reject (→ `rejected`, final — a bot cannot report
   its way past it). Re-checked under a row lock (409 `not_awaiting_approval`), written to the
   feed, audit-logged (`taurus.task.approved|rejected`). The brain can describe approvals but
   never make them (prompt `taurus_ask.v1`).

9. **Spend is as reported, never estimated.** `amount_micros` = the bot's amount × 1,000,000
   (converted on the decimal string), in the bot's currency, or null when only units were
   reported. The console sums like with like and never converts currencies or prices units.

10. **The employer hiring floor is derived, not new data.** `GET` and `POST …/ask` under
    `/v1/employer/workspaces/{workspace}/hiring-floor` read the existing pipeline tables and
    answer through the *platform* brain (prompt `taurus_hiring_ask.v1`, title-level data only,
    never candidate names). Unchanged by the workspace model.

## Consequences

- A client's keys, agents and bot token are reachable only by that workspace's members; the
  founder sees that a client workspace exists and how busy it is, not what it runs.
- A client that never adds a key gets a working floor (state, approvals) but no "Ask Taurus" and
  no voice — the platform never subsidises a client's AI usage by accident.
- A leaked ingest token lets an attacker write fake reports into one workspace only; rotation is
  one click.
- Decisions are polled with `since` strictly-greater semantics; bots should de-duplicate on
  (`task_ref`, `decided_at`).
- HQ is created lazily by `POST /v1/admin/taurus/hq`; the web calls it on the founder's first
  console visit.
- Adding a provider is config (`config/ai.php`, `ClientFactory::DEFAULT_BASE_URLS`, the settings
  `$provider` helper) plus a driver arm only for a new dialect.
