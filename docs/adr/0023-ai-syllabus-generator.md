# ADR 0023 — AI Syllabus Generator + branded document + lead-gated download (P3.5c)

- **Status:** Accepted
- **Date:** 2026-07-17
- **PRD:** §6.2 (AI Syllabus Generator), §6.1 (course-page "Download Syllabus" lead magnet)
- **Supersedes / relates to:** ADR 0020 (certificates — branded render seam), 0021 (prose fail-safe), 0022 (content AI — generate/approve pattern), the P2.1 CRM lead pipeline

## Context

Each course needs a syllabus that (a) is generated by AI from the curriculum, (b) is trainer-
approved before anyone sees it (PRD §7), (c) renders to a branded document, and (d) is downloadable
both publicly (lead-gated, name+phone) from the course page and from the student dashboard, and
(e) regenerates when the curriculum changes without disrupting running batches.

**Scope this session (tight slice of P3.5):** course-level syllabus only. Module/segment-level
syllabi, true PDF binarization, and market-driven Curriculum-Intelligence recommendations (§6.21)
are deferred.

## Decision

1. **One `syllabuses` companion table** (`unique(course_id)`): `title`, `content` (longText
   nullable, AI markdown-light prose), `status` (`draft`|`approved`), `curriculum_hash` (sha256 of
   the tree + course meta — the staleness signal), `is_stale` (bool), `render_status`
   (`pending`|`rendered`), `storage_path`, `version`, `generated_by`/`approved_by`/`approved_at`.
   `BelongsToTenant` + `tenant_id` index/FK. New enum `SyllabusStatus`; the existing
   `AiPurpose::Syllabus` is reused (no enum change). New migration `2026_07_16_200010`. The model
   pins `$table = 'syllabuses'` (Laravel would pluralize to `syllabi`).

2. **AI prose, staff-billed, fail-safe.** `Actions/Content/GenerateSyllabus` calls the gateway
   (`AiPurpose::Syllabus`, versioned prompt `resources/prompts/syllabus.v1.md`) with the course
   meta + the flattened curriculum outline (`SyllabusHasher::outline`), billing the triggering
   **staff** actor. On `AiBudgetExceeded`/transport error/empty output it **leaves `content`
   untouched** (manual authoring) and never throws (mirrors the P3.5a `ReportNarrator` fail-safe).
   Output stays **draft**. `Jobs/GenerateSyllabusJob` wraps it (queued per CLAUDE.md).

3. **Branded render behind a swappable seam.** `Support/Syllabus/SyllabusRenderer` (interface) is
   bound to `HtmlSyllabusRenderer` in `AppServiceProvider` — branded HTML (tenant colours/fonts,
   Blade `resources/views/syllabus/default.blade.php`, a tiny dependency-free markdown→HTML
   converter) stored on the render disk. A WeasyPrint/PDF binarizer swaps in behind the same
   interface later, exactly like certificates/receipts (the repo has no PDF engine — this is the
   "PDF later" reality). `Jobs/RenderSyllabus` is the queued render; it refuses to render a
   non-approved draft and **overwrites the served artifact only on success**.

4. **`ApproveSyllabus`** mirrors `ApproveQuiz`/`ApproveNotes`: idempotent; requires non-empty
   content else `ValidationException`; audits `syllabus.approved`; clears `is_stale`; dispatches
   `RenderSyllabus`. Only this action renders. It does **not** reset `render_status` to `pending`:
   on a re-approval (after an edit) the row stays `rendered` so the previously approved document
   keeps serving until the new render lands — there is no 404 window, and a failed re-render leaves
   the old artifact live rather than blanking the download. On a first approval `render_status` is
   already `pending` (nothing was ever served), so it becomes downloadable only once the render writes.

5. **Invariant — the served artifact is always the last approved render.** `isDownloadable()`
   keys off the **rendered artifact** (`render_status=rendered && storage_path`), not the current
   `status`. Because only `ApproveSyllabus` renders, a rendered artifact is by definition a
   previously-approved one. So an edit, a curriculum-change regeneration, **or a re-approval's
   in-flight re-render** all leave the last approved document serving — running batches unaffected
   (PRD §6.21). A never-approved syllabus is `pending` → not downloadable → 404. A draft's
   unapproved `content` is never rendered and never served.

6. **Regenerate on curriculum change.** A new first-class `CurriculumChanged` event is dispatched
   from the Module/Topic/Lesson admin controllers on every create/update/delete. The queued
   `RegenerateSyllabusOnCurriculumChange` listener (auto-discovered, like `SendLeadWelcomeMessage`)
   recomputes the hash; on a real change it bumps `version`, flags `is_stale`, and dispatches
   `GenerateSyllabusJob` (billed to a resolved staff user) to refresh the draft. A no-op when the
   hash is unchanged — unrelated edits don't churn.

7. **Downloads.** Public `Courses/SyllabusDownloadController` (host tenant, `throttle:10,1`) serves
   only a downloadable syllabus — else 404 with **no lead captured** — otherwise captures a
   `syllabus` lead via `CaptureLead` (CRM pipeline + welcome message; `'syllabus'` added to
   `Lead::TYPES`) and returns a short-lived signed URL. Student `Me/MySyllabusController`
   (`me/courses/{course}/syllabus`) returns a signed URL with no lead form; it resolves the course
   in-tenant-context (raw id, not route-bound) so another tenant's course 404s. Admin
   `Admin/SyllabusController` (index/show/generate/update/approve) is gated `can:manage-curriculum`.

## Consequences

- **Positive:** One approve action turns curriculum into a branded, downloadable syllabus that
  doubles as a CRM lead magnet; the human-approval gate (PRD §7) holds; the PDF engine is a single
  swap point; curriculum edits never disrupt the live download.
- **Trade-offs:** Course-level only for now (one row per course). The rendered "document" is branded
  HTML until a PDF binarizer lands. On regeneration the working `content` is a fresh draft while the
  served artifact is the last approved render — deliberate, surfaced by `is_stale` in the admin UI.
- **Deferred (owner-visible, not gaps):** module/segment-level syllabi (a future nullable
  `module_id` row on the same machinery); true PDF binarization (WeasyPrint/headless behind
  `SyllabusRenderer`); market-driven syllabus recommendations (§6.21, P4); support-desk AI (P3.5d).

## Verification

`php artisan test` — full suite **435 passing**, incl. `Feature/Syllabus/SyllabusTest` (20 tests):
AI draft stamps the hash + billed to staff; empty-output and budget-exceeded → content untouched, no
throw; hash changes with the tree; approve audits + renders the branded doc + idempotent; render job
refuses a draft; **curriculum change regenerates a new draft while the last approved stays live**;
**a re-approval's in-flight re-render keeps the last approved artifact serving (no 404 window)**;
no-op when unchanged; public download serves an approved syllabus + captures a `syllabus` lead, 404s
(no lead) when none approved, rejects without consent; student surface gated on approval + auth +
cross-tenant denial; admin gate + cross-tenant denial. Pint clean. Fresh `migrate --seed`
(`SyllabusSeeder`) attaches an approved, rendered syllabus to a seeded course (downloadable when the
render disk/MinIO is up; graceful-degrades to an approved draft otherwise). Frontend: admin
`admin/(panel)/syllabus` list + `[course]` builder, public course-page lead-gated download dialog,
student dashboard download link — `npm run typecheck`, `lint`, and `build` all pass.
Playwright `syllabus.spec.ts` covers the trainer generate→approve and the public lead-gated download.
